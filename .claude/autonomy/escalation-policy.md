# WIZOR front escalation policy (ADR-0021 D4 · порт ORIION ADR-037)

Передняя растяжка — зеркало задней ([`tripwire.yaml`](./tripwire.yaml)). Под автономным runner'ом шаг discuss/plan **не** собирает ответы founder'а на каждый форк. Агент **владеет** большинством форков — решает, логирует решение, идёт дальше. Он **останавливается и эскалирует** только для узкого явного класса.

Это контракт, который читает auto-discuss ([`/autonomy:discuss`](../commands/autonomy/discuss.md)). Операционализирует ADR-0017 §5 (эскалация — исключение, не ревью).

## Что агент ВЛАДЕЕТ (решает + логирует, НЕ спрашивает)

Каждый **implementation-** и **архитектурный** форк. Агент берёт вариант, лучший по рубрике оптимальности ([`judge-panel.md`](./judge-panel.md)), фиксирует и идёт дальше:

- Модель данных / форма схемы, layout таблиц, выбор индекса (*новая* таблица — её *миграция* всё равно ловится задней растяжкой на мёрже, но сам дизайн — решение агента).
- Алгоритм / библиотека / фреймворк в пределах залоченного стека (ADR-0011).
- Границы модулей, размещение швов, port/adapter, нейминг.
- Стратегия тестов, пороги coverage, дизайн фикстур/golden-набора.
- Какой pipeline-шаблон, как декомпозировать фазу, retry/параллелизм.
- Рефакторинги, форма внутреннего API (не-публичного), таксономия ошибок.
- Веса/пороги, детерминированные формулы Readiness Score — В ПРЕДЕЛАХ методологии GEO из `geo-domain-expert` (если веса меняют *продуктовое обещание* — это уже продукт, см. ниже).

**Логирование обязательно** (это то, что заменяет надзор founder'а):
- **Архитектурное** решение (ограничивает будущие фазы / задаёт прецедент) → новый **ADR** по house-template + `log_decision.py --kind arch --adr ADR-00NN`.
- **Всё остальное** → `log_decision.py --kind impl` → аппенд в [`DECISIONS-LOG.md`](../../.planning/_session-context/DECISIONS-LOG.md).

## Что агент ЭСКАЛИРУЕТ (стоп, пишет в RUN-QUEUE, notify, ждёт)

Только два класса. Если форк не из них — агент НЕ спрашивает, он решает.

### 1. Продуктово-рыночное поведение (территория founder, ADR-0017 §5)

Решения, требующие знания ЦА/рынка/бизнеса, которого у агента структурно нет:

- Что **видит/переживает пользователь** (UX-флоу, тексты для пользователя, какая фича входит в scope волны).
- **Прайсинг / тарифы / кредит-экономика дорожек** Tier0/Manual/Auto (любой пользовательский коммерческий термин).
- **Scope-cut**, меняющий что продукт *делает* для клиента (отложить пользовательскую способность).
- Позиционирование / мессседж / приоритет вертикали/сегмента.
- **Юр/152-ФЗ-стратегия и бренд** — DPA-политика, риск-аппетит по РКН, публичные обещания комплаенса.

> Литмус: *«Будет ли компетентный senior-инженер без рыночного контекста всё ещё гадать?»* Если правильный ответ зависит от клиентов/рынка/стратегии, а не от кода — эскалируй.

> **Уже-решённое ≠ продуктовый форк.** User-facing контент, уже зафиксированный ADR/PRD/phase-spec, **имплементируется как есть, не пере-эскалируется**: исполнение утверждённой спеки — инженерия, не новое продуктовое решение. Эскалирует не всё *видимое*, а всё *нерешённое-и-видимое* — net-new пользовательский выбор, не покрытый ни ADR, ни PRD, ни phase-spec. Копию/сценарии, которые агент должен породить сам (напр. FAQ-контент, seed-примеры), ведёт путём **автономный черновик → founder review-gate** (§6 инвариант 10: FAQ/видимый контент не авто-применяется), а НЕ up-front эскалацией.

### 2. Трипвайр-категории (тот же список, что задняя растяжка)

Миграции по существующим таблицам/RLS · auth/IAM/tenancy · billing/деньги · секреты/ключи/crypto · слом публичных контрактов · **auto-fix write-путь** · **probe-geo egress** · **ПДн/DPA/consent**. Эскалируют и на шаге **design** (не только на мёрже), потому что *подход* так же чувствителен, как и diff. Auto-fix на реальный чужой prod — вообще вне dev-автономии (ADR-0017 §6), не эскалация, а product-runtime consent.

## Процедура решения (auto-discuss гоняет по каждому форку)

1. **Перечисли** варианты форка + рекомендованный дефолт (с обоснованием по рубрике).
2. **Классифицируй:** продукт/рынок? трипвайр-категория? → **ЭСКАЛАЦИЯ**. Иначе → **agent-owned**.
3. **Owned + широкий форк** (архитектура/алгоритм/схема, варианты существенно расходятся) → запусти [judge-panel](./judge-panel.md); возьми победителя. **Owned + узкий** → рекомендованный дефолт.
4. **Залогируй** (`arch`→ADR, иначе `impl`).
5. **Эскалированный** → аппенд escalation-record в `RUN-QUEUE.md`, `PushNotification` + Telegram, и **блокируй ТОЛЬКО этот форк** — продолжай независимую работу; ставь на паузу зависимый путь до `/ack`.

## Формат escalation-record (→ RUN-QUEUE.md)

```
### ESCALATION · <phase> · <UTC ts> · <product-market|tripwire:<category>>
- Fork: <одна строка>
- Options: A) … B) … [C) …]
- Agent's lean: <вариант> — <почему, вкл. рубрику>
- Why escalated: <нужно знание рынка | необратимая категория>
- Blocks: <какие downstream-задачи ждут>
- Resolve: ответь `/ack <id> approved <option>` или `/ack <id> rejected <note>`
```

## Инварианты, которые НИКОГДА не решаются автономно в обход

Стоячие инварианты charter §6 — не «форки», а границы. Их нарушение блокирует, а не эскалируется: агент НЕ вправе выбрать вариант, ломающий read-only-границу, honest-forecast, ПДн-резидентность, probe-geo, multi-tenant-изоляцию. Конфликт scope с §6 → блок + эскалация к `architect`/founder (ADR-0017 §5), не «решение».
