## Context

Каждая фаза P0–P10 имеет свой exit-gate, проверяющий её модуль изолированно. Но **нет сквозного golden-сценария**, доказывающего, что всё собранное работает вместе от лица пользователя. Риск: можно пройти все 10 фаз с зелёными гейтами и получить набор функционально корректных, но нестыкующихся модулей (швы между контекстами — где такие баги и живут; ср. MEMORY-INDEX: P5 brand_terms не прокидывался через batch-шов → метрики инертны, поймано только адверсариальной трассировкой шва, не зелёными тестами). North Star продукта — «Verified AI-Readiness Uplift» (PRD §5) — по определению сквозной: он не проверяется ни одной отдельной фазой.

## Decision

**Definition of Done всего MVP = единый live golden-сценарий**, проходящий все контексты в порядке пользовательского пути:

```
реальный URL
  → Tier-0 аудит (P7: crawl→Score→probe→gap→патчи, async)
  → регистрация (P9: Keycloak, tenant)
  → авто-генерация + правка промптов (P6/P9)
  → probe-мониторинг (P5: dual-geo, N≥5+CI)
  → рекомендация с honest forecast (P6)
  → применённый фикс:
       • Manual track — патч копипастом → re-crawl подтверждает в HTML (P8/FR-5.5), ИЛИ
       • Auto track — WP-коннектор применил JSON-LD в <head> (P10/FR-4.1)
  → verified Readiness-delta вне полосы шума (P8/FR-5.1)
```

**Где enforced:**
- **A→B gate** — добавляется deliverable `D8: golden e2e прошёл вживую` + hard-threshold `H_golden_e2e` (обе ветки Manual и Auto). Это финальный live-акцепт перед решением о переходе в Phase B.
- **Smoke после track-границ** — сокращённый прогон релевантной части: после P7 (Tier-0 read-only путь), после P9 (Manual платный путь), после P10 (Auto путь). Ловит рассинхрон рано, не откладывая всё на A→B.
- Класс — **live-only** (ADR-0022): требует реального URL, funded-ключей, test-WP, прода (P6.5). Оформлен как gate-blocker, не тихий deferred.

## Consequences

- **Позитивно:** «собрался ли рабочий продукт» получает однозначный бинарный ответ — один сценарий, который либо проходит вживую, либо нет. North Star становится проверяемым, не декларативным.
- **Позитивно:** швы между контекстами (частый источник багов) покрыты end-to-end, а не только контрактными стабами.
- **Позитивно:** track-smoke'и (после P7/P9/P10) ловят интеграционные щели рано — дешевле, чем на A→B.
- **Компромисс:** golden e2e дорог (реальные сервисы, полный путь, минуты на прогон) и хрупок (зависит от внешних LLM/WP). Митигируется: малый golden-набор (ADR-0018), запуск на track-границах (не на каждом PR), явный blocked при отсутствии ресурса.
- **Риск:** внешняя флакость (LLM/прокси/WP недоступны) может валить smoke не по вине кода. Митигируется fault-isolation (уже в P4/P5) и ретраями; при устойчивом внешнем сбое — evidence с пометкой external-flake, не блок.
- **Открывает:** golden-сценарий — основа регрессионного пакета для Phase B (агентства масштабируют тот же путь на N сайтов).

## Alternatives considered

| Альтернатива | Pro | Contra | Почему отклонили |
|---|---|---|---|
| Пофазных exit-gate'ов достаточно | Ничего добавлять | Не проверяют связность; швы между контекстами не покрыты; North Star не enforced | Можно собрать нестыкующиеся модули с зелёными гейтами |
| Golden e2e только после P10 (один раз) | Дёшево | Рассинхрон обнаруживается в самом конце; дорогая отладка | Track-smoke'и ловят раньше и дешевле |
| Три отдельных полных e2e (Tier0/Manual/Auto) на каждой границе | Строже всего | Дороже по live-gold-ресурсам; дублирование прогонов | Один golden + сокращённые track-smoke'и достаточно |
