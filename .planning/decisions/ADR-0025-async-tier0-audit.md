## Context

P7 AC-1 (исходно) требовал полный Tier-0 аудит **синхронно за <90 сек**: crawl сайта + Score + probe (1×4 модели) + competitive gap + патчи. Но competitive gap сам требует probe-ответов (найти цитируемых конкурентов) + краул этих конкурентов. Реалистичная стоимость: Playwright-краул сайта + 4 LLM-вызова + краул 3–5 конкурентов = **3–8 минут**, не 90 секунд. Жёсткий синхронный AC оставлял два плохих выхода: (1) урезать глубину до бесполезности (Score без Visibility/gap — слабый лид-магнит); (2) «проходить» тест на крошечном моке — известный pitfall `test-masking` (MEMORY-INDEX: P4/P5), при котором зелёный тест скрывает нерабочий прод-путь. HTTP-запрос, висящий 5 минут, к тому же ненадёжен (таймауты прокси/балансировщика).

## Decision

**Асинхронная job-модель с двумя порогами наполнения:**

- `POST /api/public/audit {url}` — валидирует URL, ставит job в очередь (Celery), **мгновенно** возвращает `{job_id, status: "queued"}`.
- Результат-страница (frontend) поллит `GET /api/public/audit/{job_id}` и наполняется **поэтапно**:
  - **Порог 1 (≤90 сек):** `score`, `components[]`, copy-paste `patches[]` (быстрый детерминированный слой — crawl + Score + генерация патчей).
  - **Порог 2 (≤5 мин):** `visibility_preview` (probe 1×4 модели), `competitors_gap` (probe + краул конкурентов). До готовности — UI показывает прогресс-плейсхолдеры.
- Job-стадии видны в ответе (`stages: {score: done, visibility: running, gap: queued}`) — честный прогресс, не спиннер вслепую.
- Rate-limit (per-IP) применяется на `POST` (постановка job), не на polling.

**AC-1 переписывается** на два порога: (а) `score`+`patches` доступны в `GET job` ≤90с; (б) `visibility_preview`+`competitors_gap` доступны ≤5мин. Оба — измеримо, честно, без урезания глубины.

## Consequences

- **Позитивно:** лучший UX — пользователь сразу видит движение (Score+патчи быстро), тяжёлое догружается без блокировки. Прогресс честный (стадии видны).
- **Позитивно:** честная инженерия — AC отражает реальную стоимость, не вынуждает мок-маскировку; полная глубина gap-анализа сохранена.
- **Позитивно:** надёжность — нет висящих 5-минутных HTTP; polling переживает сетевые сбои.
- **Компромисс:** frontend сложнее (polling + поэтапный рендер + плейсхолдеры vs один ответ). Оправдано — это lead-magnet, UX критичен.
- **Компромисс:** job-инфраструктура для anon-трафика (Celery + Redis + TTL-чистка) — но она уже есть (P1) и нужна для regular-мониторинга.
- **Открывает:** тот же async-паттerн переиспользуется для авторизованного on-demand re-audit (P8/P9).

## Alternatives considered

| Альтернатива | Pro | Contra | Почему отклонили |
|---|---|---|---|
| Синхронно <90с, урезать глубину (≤5 стр, 1 модель, gap по кэшу) | Просто | Результат беден → слабый лид-магнит; и всё равно рискует таймаутом | Tier-0 — витрина продукта, глубина важна |
| Синхронно, «проходить» на моке | Зелёный тест | test-masking: прод-путь не проверен; известный pitfall | Прямо запрещено доктриной evidence-gated |
| Email-отчёт (URL+email → письмо) | Собирает лиды | Email-барьер против чистого no-auth PLG; требует согласие на ПДн уже в Tier-0 | Трение против PLG-входа; ПДн-осложнение |
| WebSocket вместо polling | Реактивнее | Сложнее инфра (sticky sessions за балансировщиком) | Polling проще и достаточно для минутных стадий |
